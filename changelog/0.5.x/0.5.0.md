# 0.5.0 — 2026-07-02

## Added

- **`src/services/status-adapters/firehydrant-adapter.ts`** — fetches the `{page}/data/payload.json` feed every Firehydrant-hosted status page serves (the page SPA's own data source) and normalizes it into the Statuspage shapes. The payload has no top-level status, so the indicator derives from active incidents' severity (`SEV1` → critical, `SEV2` → major, `SEV3`/`SEV4` → minor, `MAINTENANCE` → none, unknown → minor) and component health from active incidents' conditions canonicalized through the page's condition table; `MAINTENANCE` items feed the scheduled-maintenances stream. History is unbounded, so the incidents endpoint caps at the 50 newest — parity with Statuspage `/api/v2/incidents.json` ([#14](https://github.com/cyanheads/devops-status-mcp-server/issues/14)).
- **`firehydrant` api_type** — `VendorApiType`, `VendorEntry`, and `ResolvedVendor` unions extended; `status-dispatch.ts` routes it. Any future Firehydrant vendor slots in via its page URL alone.
- **Adapter tests** — `tests/services/status-adapters/firehydrant-adapter.test.ts` over a live-capture fixture (`fixtures/firehydrant-redis.json`), plus dispatch routing and registry-integrity assertions.

## Changed

- **Backend lists** — server instructions, the `devops_status_check` description, the vendor-entry resource `api_type` description, README, and the plugin `longDescription` now name the Firehydrant backend.

## Fixed

- **`redis-cloud`** — the page (`status.redis.io`) moved from Atlassian Statuspage to Firehydrant, so `/api/v2/status.json` returned the SPA's HTML shell with HTTP 200 and the fetch surfaced as a JSON parse error; the entry is re-typed to `api_type: 'firehydrant'` on the same page URL ([#14](https://github.com/cyanheads/devops-status-mcp-server/issues/14)).
