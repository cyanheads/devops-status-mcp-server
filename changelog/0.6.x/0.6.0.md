# 0.6.0 — 2026-07-30

## Added

- **`devops_check_dns`** — `resolver_results[]` gains a typed `status` and `status_by_type` (`ok` / `nodata` / `nxdomain` / `servfail` / `refused` / `timeout` / `error`), so NXDOMAIN, SERVFAIL, and a genuinely missing record no longer report as byte-identical "no records found" ([#31](https://github.com/cyanheads/devops-status-mcp-server/issues/31)).
- **`devops_check_dns`** — `propagation_discrepancies[]` gains `kind` (`value_variation` | `partial_resolution`) and `status_by_resolver`. `value_variation` (every resolver answered, values differ — anycast/geo-steering) is recorded but no longer flagged; only `partial_resolution` (some resolvers answered, some returned nothing) raises a flag ([#35](https://github.com/cyanheads/devops-status-mcp-server/issues/35)).
- **`devops_check_dns`** — `records_source` names which resolver's answers populated the top-level `records` field.
- **`devops_check_certs`** — `cert.hostname_verification_error` and `cert.authorization_error` surface Node's hostname check and OpenSSL chain-verification result; either sets `status` to `critical` ([#26](https://github.com/cyanheads/devops-status-mcp-server/issues/26)).
- **`devops_check_certs`** — `cert.chain_depth_unavailable_reason` explains a null `chain_depth` ([#27](https://github.com/cyanheads/devops-status-mcp-server/issues/27)).

## Changed

- **`devops_check_certs`** — `cert.chain_depth` is `number | null` instead of always a number. `getPeerCertificate(true).issuerCertificate` is unpopulated on Bun even for CA-issued chains, so the field previously reported a confident `1` for chains it never measured. `1` no longer means self-signed — that's now `authorization_error: "DEPTH_ZERO_SELF_SIGNED_CERT"` ([#27](https://github.com/cyanheads/devops-status-mcp-server/issues/27)).
- **`devops_check_certs`** — self-signed and untrusted-root certificates now resolve to `critical` instead of `warning`, matching where expiry already lands — both are hard client-side rejections.
- **`devops_check_dns`** — `records` / `records_source` fall back to the first resolver that returned records when the primary resolver failed, instead of always reading `resolver_results[0]`.
- **`devops_check_dns`** — the domain-level `error` is now derived across every resolver — reserved for "no resolver returned records at all" — instead of the first resolver's message, so a split outcome (one NXDOMAIN, one SERVFAIL) stays visible.

## Fixed

- **`devops_check_dns`** — `queryResolver()` swallowed `ENOTFOUND` and `ESERVFAIL` alongside `ENODATA`, so a nonexistent domain, a DNSSEC validation failure, and a genuinely missing record type all produced the same "no records found" output ([#31](https://github.com/cyanheads/devops-status-mcp-server/issues/31)).
- **`devops_check_dns`** — `findDiscrepancies()` flagged any per-resolver value difference as a propagation mismatch, reporting an in-flight DNS change for anycast/geo-steered domains (e.g. CDN-fronted hostnames) that were never mid-change ([#35](https://github.com/cyanheads/devops-status-mcp-server/issues/35)).
- **`devops_check_certs`** — `inspectCert()` connected with `checkServerIdentity: () => undefined`, discarding Node's hostname validation, so a certificate that doesn't cover the requested domain (e.g. `wrong.host.badssl.com`) could report `status: "ok"` ([#26](https://github.com/cyanheads/devops-status-mcp-server/issues/26)).
- **`devops_check_certs`** — an untrusted-root certificate produced no flag at all, since the self-signed heuristic (`issuer === subject`) doesn't fire when the issuer is a real but untrusted CA ([#26](https://github.com/cyanheads/devops-status-mcp-server/issues/26)).
