# 0.5.7 — 2026-07-30

## Added

- **`devops_get_incidents`** gains `nextOffset` and `upstreamCeiling` enrichment fields ([#24](https://github.com/cyanheads/devops-status-mcp-server/issues/24), [#25](https://github.com/cyanheads/devops-status-mcp-server/issues/25)). `nextOffset` carries the already-computed continuation offset for a truncated page; its absence is the stop condition for an agent paging in a loop. `upstreamCeiling` reports when a vendor's own incident feed — not this tool's window — bounded the result: Statuspage and Slack both cap `incidents.json`/`history` at 50 records with no working `?page=` parameter, so incidents older than the oldest one returned are unreachable at any offset and only browsable on the vendor's own status page.
- **`devops_status_check`** and **`devops_watch_stack`** declare a `notice` enrichment field carrying the capped-component guidance `fetchVendorResults()` already composed (which components were omitted, how to reach them via `component_filter`/`component_limit`) ([#24](https://github.com/cyanheads/devops-status-mcp-server/issues/24)).
- **`backendHistory()`** in `status-dispatch.ts` states each backend's incident ceiling, resolved-history reach, and maintenance-window support, exhaustive over `api_type` — Statuspage and Slack cap at 50 records, AWS Health has no resolution lifecycle and no maintenance feed, Status.io serves current incidents only, FireHydrant is unbounded.

## Changed

- **`devops_get_incidents`** empty-result guidance is now a function of the filter, offset, and backend that produced the empty set, instead of one static suggestion: an out-of-range `offset` names the valid range, a filter the resolved backend can never satisfy (e.g. `resolved` against AWS's lifecycle-less feed, `scheduled` against AWS or Slack) states that directly, and the suggested filters never include the one just used.

## Fixed

- **`devops_get_incidents`** previously composed continuation guidance and vendor-ceiling context but declared neither `nextOffset` nor `notice` in its enrichment schema, so `output.extend(enrichment)` stripped both before they reached `structuredContent` or the `content[]` trailer ([#24](https://github.com/cyanheads/devops-status-mcp-server/issues/24)).
- **`devops_status_check`** and **`devops_watch_stack`** had the identical defect for their capped-component guidance — declared `truncated`/`shown`/`cap`/`totalCount` but not `notice`, so the composed guidance was silently dropped ([#24](https://github.com/cyanheads/devops-status-mcp-server/issues/24)).
- **`devops_get_incidents`** treated a full 50-record Statuspage/Slack response as complete incident history with no disclosure that older incidents exist and are unreachable through the tool ([#25](https://github.com/cyanheads/devops-status-mcp-server/issues/25)).
